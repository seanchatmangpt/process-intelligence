## 1. Conformance Techniques Taxonomy

PM4Py implements seven orthogonal conformance checking methods, each with distinct failure modes, scalability profiles, and epistemological assumptions.

### 1.1 Token-Based Replay (TBR)

**Conceptual Foundation:**
Tokens flow through a Petri Net. A trace is replayed by attempting to fire transitions in order. If a transition cannot fire (required input place has no token), a token is artificially injected (missing token). If tokens remain in places other than the final sink after the trace completes, they are counted (remaining tokens).

**Mathematical Definition:**

For a trace σ and net N with initial marking m_i and final marking m_f:
- **p** = tokens produced during replay (initial tokens + tokens generated by transitions)
- **c** = tokens consumed (required to fire transitions)
- **m** = missing tokens (injected to enable blocked transitions)
- **r** = remaining tokens (left in non-sink places at termination)

**Fitness (per-trace):**
$$f(\sigma, N) = \frac{1}{2}\left(1 - \frac{m}{c}\right) + \frac{1}{2}\left(1 - \frac{r}{p}\right)$$

**Aggregate Fitness (log):**
$$f(L, N) = \frac{1}{2}\left(1 - \frac{\sum_{\sigma \in L} m_{\sigma}}{\sum_{\sigma \in L} c_{\sigma}}\right) + \frac{1}{2}\left(1 - \frac{\sum_{\sigma \in L} r_{\sigma}}{\sum_{\sigma \in L} p_{\sigma}}\right)$$

**PM4Py Functions:**
- `fitness_token_based_replay(log, net, im, fm)` → Dict
  - Returns: `log_fitness` (aggregate), `average_trace_fitness` (per-case mean), `min_trace_fitness`, `max_trace_fitness`, `all_activating` (bool)
- `conformance_diagnostics_token_based_replay(log, net, im, fm)` → List[Dict(per-trace)]
  - Returns per-trace: `trace_id`, `fitness`, `missing_tokens`, `remaining_tokens`, `produced`, `consumed`
- `replay_prefix_tbr(log, net, im, fm, prefix_length)` → Marking
  - Returns final marking after replaying a prefix of the trace

**Complexity:**
- **Time:** O(|L| × |σ| × |N|) where |L| = log size, |σ| = avg trace length, |N| = net size
- **Space:** O(|N|) (single marking maintained per trace)
- **Scalability:** Linear in log size; **fastest conformance method**

**Epistemology:**
- Binary token model: a place either has a token or does not
- **No data flow:** Ignores attribute conditions, variable assignments, payload semantics
- **No control guards:** Cannot model conditional routing or data dependencies
- **Overly Permissive:** A trace may pass TBR while violating implicit control constraints

**Failure Conditions:**

1. **Missing Start Activity:** If the trace omits the first activity, TBR injects tokens into the source place.
   - Fitness penalty: 50% × (1/total_consumed)
   - Example: "Approve, Ship" (missing "Register") on a 3-activity net reduces fitness to 0.667

2. **Activity Out of Order:** TBR will inject tokens upstream to enable the activity.
   - Penalty proportional to distance from correct position in model

3. **Infinite Loops in Net:** If the net contains loops, a short trace may leave tokens in loop places.
   - Remaining tokens counted; fitness reduced

4. **Non-Determinism:** If multiple paths exist, TBR takes the first enabled transition.
   - No backtracking; may report lower fitness than optimal

5. **Deadlock in Trace:** If no transition can fire, TBR injects a missing token.
   - Penalty incurred regardless of whether deadlock was legitimate

**Constraints:**
- Requires Petri Net + Initial Marking + Final Marking
- No variant selection or cost parameterization
- Fixed cost model: all missing/remaining tokens equally weighted

### 1.2 Alignment-Based Conformance

**Conceptual Foundation:**
Alignment treats the problem as sequence matching. A log trace σ and a model M are aligned by finding a sequence of moves that minimizes total deviation cost. Each move is classified:
- **Synchronous:** Activity in log matches transition in model (cost = 0)
- **Move in Log:** Activity in log, no matching model transition (cost > 0)
- **Move in Model:** Transition in model, no activity in log (cost > 0)

**Mathematical Definition:**

An alignment γ is a pair sequence:
$$\gamma = \left[(t_1, a_1), (t_2, a_2), \ldots, (t_n, a_n)\right]$$

where $(t_i, a_i) \in (T \cup \{\gg\}) \times (\Sigma \cup \{\gg\})$.

Cost function:
- $c(t, a) = 0$ if t matches a (synchronous)
- $c(\gg, a) = \text{log\_cost}$ (default: 1) for log deviation
- $c(t, \gg) = \text{model\_cost}$ (default: 1) for model deviation

**Optimal Alignment:**
$$\gamma^* = \operatorname{argmin}_{\gamma} \sum_{(t, a) \in \gamma} c(t, a)$$

**Fitness Metric (Adriansyah 2014):**
$$\text{fitness} = 1 - \frac{\text{alignment\_cost}}{2 \times |σ|}$$

where |σ| = trace length.

**Precision Metric:**
$$\text{precision} = 1 - \frac{\text{total\_model\_moves}}{\text{total\_log\_moves} + \text{total\_model\_moves}}$$

Measures overfitting: high precision means the model does not allow much behavior beyond what was observed.

**PM4Py Functions:**
- `fitness_alignments(log, net, im, fm)` → Dict
  - Returns: `log_fitness`, `average_trace_fitness`, `min_trace_fitness`, `max_trace_fitness`
- `precision_alignments(log, net, im, fm)` → float
  - Returns single precision value for entire log
- `conformance_diagnostics_alignments(log, net, im, fm)` → List[Dict(per-trace)]
  - Returns per-trace: `trace_id`, `alignment` (list of moves), `cost`, `fitness`

**Parameters:**
- `variant_str: str` — Alignment algorithm selection
  - Default: `'dijkstra_no_heuristic'` (A* with reachability heuristic)
  - Options: `'dijkstra'` (plain A*), `'state_equation_a_star'`, `'twf'` (transfer-follow)
- `multi_processing: bool` — Parallel trace processing (default: False)

**Complexity:**
- **Time:** O(|L| × |σ| × |N|²) with A* heuristic (or worse without)
- **Space:** O(|σ| × |N|) (alignment search state)
- **Scalability:** **Cubic** in model size; **intractable** on logs > 100k events or nets with >1k transitions

**Epistemology:**
- Full path semantics: captures temporal ordering and control flow
- **Cost-based deviation:** Quantifies impact of each deviation
- **Deterministic:** Always finds optimal or near-optimal alignment (with A*)
- **Enables Precision:** Measures model overfitting, not just fitness

**Failure Conditions:**

1. **State Explosion:** Complex nets with concurrency generate exponential state space.
   - Alignment search times out or returns heuristic approximation
   - Example: net with 10 concurrent transitions × 10-activity trace = 10^10 states

2. **Infeasible Alignment:** If model and log diverge completely, alignment cost = 2 × |σ|.
   - Fitness = 0; no information on where divergence occurs

3. **Unobserved Paths:** If model allows a path that never occurs in log, precision penalizes the model.
   - Example: model has "Ship OR Reject" but all cases ship → precision < 1.0

4. **Weak Heuristic:** Without good reachability heuristic, A* degenerates to Dijkstra.
   - Search becomes exhaustive; can exceed time budget

5. **Loop Unfolding:** Model loops are unfolded up to log trace length.
   - If log has traces >20 events with deep loops, search space explodes

**Constraints:**
- Requires complete Petri Net (all places, transitions reachable)
- No support for weighted/probabilistic transitions
- Cost model is static; cannot be learned from log deviations
- A* heuristic depends on reachability matrix; lazy computation adds overhead

### 1.3 Footprints-Based Conformance

**Conceptual Foundation:**
Footprints capture the **structural relations** between activities: directly follows, never follows, parallel (both orders observed), etc. A footprint matrix is computed for both log and model, then compared element-wise.

**Mathematical Definition:**

Footprints = {successors, predecessors, concurrency pairs}.

For activities a, b:
- **→:** a directly followed by b in some trace
- **#:** a and b never appear together in any trace
- **||:** both a→b and b→a observed (concurrent)
- **→** (unsymmetric): a→b but never b→a

**PM4Py Functions:**
- `fitness_footprints(log, net, im, fm)` → Dict
  - Returns: `log_fitness` (% of log footprints matched in model)
- `precision_footprints(log, net, im, fm)` → float
  - Returns: % of model footprints observed in log
- `conformance_diagnostics_footprints(log, net, im, fm)` → List[Dict(per-trace)]
  - Returns: per-trace violations (missing/extra footprint pairs)

**Complexity:**
- **Time:** O(|L| × |σ| × |A|²) where |A| = activity alphabet
- **Space:** O(|A|²) for footprint matrices
- **Scalability:** **Quadratic** in alphabet size; scales well for <1k activities

**Epistemology:**
- **Structural only:** No temporal ordering beyond directly-follows
- **Lightweight:** No net exploration; only log scan
- **Coarse-grained:** Misses cycle detection, loop depth, concurrency semantics
- **Robust to Noise:** Rare activities don't break footprints

**Failure Conditions:**

1. **Silent Transitions:** If model has invisible transitions, footprints don't match log.
   - Example: model has "A → τ → B" but log shows "A → B"
   - Footprints report extra edge in model

2. **Duplicate Activities:** If an activity repeats (loop), footprints collapse into a single node.
   - Cannot distinguish "A, B, A" from "A, B" in footprint view

3. **Implicit Concurrency:** If log shows both "A→B" and "B→A", footprints mark concurrent.
   - But model may enforce strict order; footprints don't validate causality

4. **Unobserved Paths:** Common paths in model never appearing in log inflate precision penalty.
   - Example: model has 5 paths, log only exercises 2 → precision = 0.4

5. **Activity Synonym:** If log uses "Approve" and model uses "Accept", footprints don't link them.
   - Requires manual activity mapping

**Constraints:**
- No full temporal semantics; only directly-follows relations
- Cannot validate blocking or deadlock
- Activity labels must match exactly (case-sensitive)
- No support for resource or attribute conditions

### 1.4 Declare Conformance

**Conceptual Foundation:**
Declare models are sets of **constraints** (templates) over activities. Conformance is checked by evaluating constraint violations on a trace.

**Supported Templates (per Pesic et al.):**
- **Existence:** Activity must occur (at least once)
- **Response:** If A, then eventually B
- **Precedence:** B only if preceded by A
- **Succession:** A followed by B (both response + precedence)
- **Alternate Precedence/Response:** A only if directly preceded by B (no interleaving)
- **Chain Precedence/Response:** Tighter alternate (immediately preceded)
- **CoExistence:** A ↔ B (if one, then the other)
- **NotCoExistence:** Not both A and B in same case
- **Absence:** Activity must not occur
- **Init:** Case starts with activity

**PM4Py Functions:**
- `conformance_declare(log, declare_model, case_id_key, activity_key, resource_key)` → Dict or DataFrame
  - Returns: per-trace violation counts for each template
  - Option: `include_affected_cases: bool` — List trace IDs with violations

**Complexity:**
- **Time:** O(|L| × |σ| × |constraints|)
- **Space:** O(|constraints|)
- **Scalability:** Linear; **fastest for large logs**

**Epistemology:**
- **Constraint-centric:** Model is a set of rules, not a process structure
- **Negative semantics:** Detects violations, not proofs of conformance
- **Post-hoc only:** Cannot generate new constraints from data
- **No synthesis:** Output is violation report, not a unified model

**Failure Conditions:**

1. **Conflicting Constraints:** If constraints contradict (e.g., "A must occur" AND "A must not occur"), all traces violate.
   - Conformance = 0; no diagnostic info

2. **Incomplete Specification:** Declare models often under-specify; many traces pass even if non-conforming.
   - High false-negative rate if constraints are sparse

3. **Resource-Aware Constraints:** PM4Py Declare does not support roles/resources well.
   - Template `response(A, B, r_A, r_B)` (B must be done by different resource than A) not implemented

4. **Temporal Constraints:** Declare supports existence/order but not time bounds.
   - Cannot express "within 24 hours"

5. **Attribute-Based:** Declare cannot condition on event attributes (e.g., "if amount > 1000, then approval").
   - Requires manual log enrichment

### 1.5 Log Skeleton Conformance

**Conceptual Foundation:**
A log skeleton is a lightweight model derived from a log itself. It captures equivalence classes of activities, predecessors/successors, and always/never together relations.

**Components:**
- **Equivalence Classes:** Activities with identical behavior (e.g., both "Approve" and "Review" behave identically)
- **Predecessor/Successor Sets:** For each activity, the set of activities that must precede/follow
- **Always/Never Together:** Pairs of activities that always or never appear in the same case

**PM4Py Functions:**
- `discover_log_skeleton(log, noise_threshold)` → Dict
  - Returns: skeleton structure (equivalence, pred/succ, together relations)
- `conformance_log_skeleton(log, skeleton)` → Dict or DataFrame
  - Returns: per-trace violations of skeleton constraints

**Complexity:**
- **Time:** O(|L| × |σ|)
- **Space:** O(|A|²) for relation matrices
- **Scalability:** Linear; **most efficient**

**Epistemology:**
- **Log-derived:** Model is extracted from data, not given externally
- **Conservative:** Only captures relations that appear in log
- **No Synthesis:** Cannot discover new behaviors
- **Comparison-only:** Useful for detecting drift, not validation

**Failure Conditions:**

1. **Overfitting:** Skeleton from full log will match full log perfectly but fail on new variants.
   - Fitness = 1.0 always (tautology)

2. **Noise-Induced Classes:** If rare variants exist, skeleton fragments.
   - High equivalence class count; sparse predecessors

3. **Empty Cells:** If some predecessor/successor pairs never occur, skeleton marks as "never together".
   - New log variants violate skeleton

4. **Incomplete Log:** If log doesn't exercise all paths, skeleton is a lower bound on conformance.
   - Cannot validate unobserved behaviors

### 1.6 Temporal Profile Conformance

**Conceptual Foundation:**
Temporal profile captures **min/max waiting times** between consecutive activities. Conformance checks if observed durations fall within bounds.

**Mathematical Definition:**

For each directly-follows pair (a, b):
- **τ_min(a,b)** = minimum observed duration
- **τ_max(a,b)** = maximum observed duration
- **zeta** = penalty weight for violations

Violation cost = zeta × max(0, observed_duration - τ_max)

**PM4Py Functions:**
- `discover_temporal_profile(log, activity_key, timestamp_key, case_id_key)` → Dict
  - Returns: Dict[(activity_a, activity_b) → (min_duration, max_duration)]
- `conformance_temporal_profile(log, profile, zeta)` → Dict or DataFrame
  - Returns: per-trace temporal deviations, cumulative delay

**Parameters:**
- `zeta: float` (default: 1.0) — Severity multiplier for violations
- `threshold_events: int` — Ignore pairs with <threshold occurrences

**Complexity:**
- **Time:** O(|L| × |σ|)
- **Space:** O(|A|²)
- **Scalability:** Linear

**Epistemology:**
- **Empirical bounds:** Assumes min/max from log are ground truth
- **No distribution:** Only captures edges (min/max), not variance
- **Reactive:** Cannot enforce SLAs or predict delays

**Failure Conditions:**

1. **Outliers in Log:** Single slow trace sets τ_max; all future fast traces flag violations.
   - Noise propagates to conformance metric

2. **Insufficient Data:** If few (a, b) pairs observed, bounds are unreliable.
   - May be too strict or too loose

3. **No Variance Model:** Temporal profile doesn't capture percentiles.
   - Cannot say "95% of cases complete within X hours"

4. **Calendar-Agnostic:** Durations measured wall-clock; ignores business hours.
   - "24 hours" duration = 1 business day but 2 calendar days

### 1.7 OCEL Conformance (Object-Centric)

**Conceptual Foundation:**
OCEL logs track multiple interacting objects. Conformance checks validate:
- Event-to-object relations (which objects are involved in which events)
- Object lifecycle ordering (objects follow a defined sequence)
- Object-to-object interactions

**PM4Py Functions:**
- `conformance_ocdfg(ocel, ocdfg)` → Dict
  - Compares observed event-object interactions against OCDFG model
  - Returns: event coverage, object interaction fitness
- `conformance_etot(ocel, etot)` → Dict
  - Event-to-object relation conformance
- `conformance_otg(ocel, otg)` → Dict
  - Object-type-to-object-type graph conformance

**Complexity:**
- **Time:** O(|events| × |objects| × |relations|)
- **Space:** O(|objects|²)
- **Scalability:** Depends on object cardinality; degrades for >10k objects

**Epistemology:**
- **Structural fitness:** No token replay semantics for object-centric nets
- **No lifecycle validation:** Cannot enforce object state machines
- **Empirical only:** Conformance = "observed in log", not "required by model"

**Failure Conditions:**

1. **Object Lifecycle Violations:** OCEL doesn't validate that objects follow defined state machines.
   - Can create, then create again; no deadlock detection

2. **Many-to-Many Ambiguity:** An event linked to multiple objects may have unclear causality.
   - Cannot determine if one object caused another's state change

3. **Missing Object Types:** If log introduces new object type, OCEL structure changes.
   - Model assumes fixed object vocabulary

## 2. Quality Dimensions & Metrics

### 2.1 Fitness

**Definition:** Proportion of the log that can be replayed without deviation.

**Interpretation:**
- **1.0:** Perfect conformance; log is lawful
- **0.8-0.99:** Acceptable; minor deviations
- **0.5-0.79:** Suspect; significant deviations
- **<0.5:** Non-conforming; model or log is invalid

**Calculation by Method:**
| Method | Fitness Formula |
|--------|-----------------|
| **TBR** | 0.5 × (1 - m/c) + 0.5 × (1 - r/p) |
| **Alignment** | 1 - (cost / (2 × \|σ\|)) |
| **Footprints** | # matched footprints / # log footprints |
| **Declare** | 1 - (violations / total_constraints) |
| **Temporal** | 1 - sum(zeta × violations) |
| **OCEL** | # observed relations / # expected relations |

### 2.2 Precision

**Definition:** Proportion of model behavior that is observed in the log.

**Interpretation:**
- **1.0:** Model is tight; no overfitting
- **0.8-0.99:** Acceptable; model allows some unseen behavior
- **0.5-0.79:** Suspect; model allows much unobserved behavior
- **<0.5:** Severe overfitting; model is disconnected from data

**Calculation by Method:**
| Method | Precision Formula |
|--------|------------------|
| **Alignment** | 1 - (moves_in_model / (moves_in_log + moves_in_model)) |
| **Footprints** | # observed pairs / # model pairs |
| **TBR** | Generalization = 1 - (produced / log_size) |
| **Declare** | Constraint coverage (% of constraints satisfied) |
| **OCEL** | # observed object interactions / # allowed interactions |

### 2.3 Generalization

**Definition:** Robustness to unseen traces; inverse of overfitting.

**Calculation (TBR):**
$$\text{generalization} = 1 - \frac{\text{produced\_tokens}}{\text{log\_size}}$$

Higher = more resilient to variant explosion.

### 2.4 Simplicity

**Definition:** Structural complexity of the model.

**Calculation (Petri Net):**
$$\text{simplicity} = \frac{1}{|P| + |T| + |F|}$$

Used to select between competing models with similar fitness/precision.

## 3. Failure Modes & Edge Cases

### 3.1 Model-Induced Failures

| Failure | Symptom | Root Cause | Mitigation |
|---------|---------|-----------|-----------|
| **Unsound Net** | Fitness = 0 for all traces; persistent missing tokens | Petri net violates soundness (deadlock, livelock) | Use Inductive Miner; verify soundness before conformance |
| **Dead Transitions** | Model path unexercised; precision < 0.5 | Transition unreachable from initial marking | Check net reachability; reduce/simplify |
| **Over-Concurrency** | Alignment state explosion; timeout | Multiple concurrent paths; exponential unfolding | Use TBR instead; abstract net with reduction |
| **Duplicate Activities** | Alignment confuses multiple instances | Model has multiple transitions with same label | Use process tree (unique labels); or relabel |

### 3.2 Log-Induced Failures

| Failure | Symptom | Root Cause | Mitigation |
|---------|---------|-----------|-----------|
| **Missing Start Events** | TBR injects tokens; fitness penalty | Cases don't record initial activity | Insert artificial start or filter prefix |
| **Out-of-Order Events** | Alignment detects deviations; cost high | Timestamp errors, clock skew, parallel submission | Resync timestamps; use OTel traces as source |
| **Duplicate Events** | Conformance fails; extra tokens/transitions | Same activity recorded twice per system error | Dedup by (case_id, activity, timestamp) |
| **Activity Synonyms** | Footprints/Declare don't link | Log uses "Approve" and "Accept" interchangeably | Normalize labels via mapping; use activity ontology |
| **Missing Attributes** | Resource/temporal checks fail | Log incompleteness; sparse attributes | Enrich log with external data or accept sparse model |

### 3.3 Scalability Failures

| Limit | Threshold | Method Affected | Solution |
|-------|-----------|-----------------|----------|
| **Log Size** | >1M events | All (TBR slowest) | Sample log; stratified by variant |
| **Case Count** | >100k cases | Alignment (state explosion) | Use TBR; decrease log size |
| **Activity Alphabet** | >1k unique | Alignment, footprints (|A|² space) | Abstract activities; use DFG filtering |
| **Model Complexity** | >500 transitions | Visualization, alignment | Decompose; use sub-nets |
| **Trace Variants** | >100k unique | Genetic miner, ILP (optimization intractable) | Use Inductive; accept noise |

## 4. Conformance Validation Protocol

### 4.1 Multi-Metric Validation Workflow

To avoid single-point failure, apply **all seven techniques** in sequence:

```
1. Token-Based Replay (TBR)
   └─ If fitness < 0.8: STOP; model is fundamentally non-conformant
   
2. Alignment-Based
   └─ If fitness < TBR fitness by >10%: investigate state explosion
   
3. Footprints-Based
   └─ Lightweight sanity check; should agree with TBR in direction
   
4. Declare Conformance
   └─ Validate constraint violations; qualitative assessment
   
5. Temporal Profile
   └─ Check for timing anomalies; SLA violations
   
6. Log Skeleton
   └─ Validate structural invariants; drift detection
   
7. OCEL Conformance (if object-centric)
   └─ Validate object lifecycle and interactions
```

### 4.2 Decision Tree: Which Method to Use?

**Q1: Is the log case-centric or object-centric?**
- Case-centric → Methods 1-6
- Object-centric → Method 7 (OCEL) + discovery via OCDFG/OCPN

**Q2: What is the log size?**
- <10k events → Use alignment (precise cost breakdown)
- 10k-1M events → Use TBR (linear scaling) + footprints (validation)
- >1M events → Use footprints + temporal profile (both O(|L|))

**Q3: What is the model size?**
- <50 transitions → Use alignment (state space manageable)
- 50-500 transitions → Use TBR + footprints (avoid explosion)
- >500 transitions → Use TBR only; visualize sub-nets separately

**Q4: Do you need precision (model overfitting detection)?**
- Yes → Use alignment-based precision
- No (fitness only) → Use TBR + footprints

**Q5: Is timing critical?**
- Yes (SLAs, compliance) → Add temporal profile conformance
- No → Omit temporal

## 5. Failure Condition Taxonomy

### 5.1 Recoverable Failures (Replayable with Cost)

These traces deviate but can be replayed with token injection or move insertion:

| Deviation Type | TBR Impact | Alignment Impact | Declare Impact | Remediation |
|---|---|---|---|---|
| Missing start activity | +1 missing token | +cost for log move | -1 init constraint | Insert artificial start in log |
| Activity out-of-order | +missing, remaining tokens | +2× move cost | +1 response violation | Validate temporal order; may be legitimate concurrency |
| Duplicate activity (rework) | Depends on net loops | Loop unfolding cost | Repeat constraint validation | Check if rework is expected |
| Extra activity (not in model) | Remaining token if no sink transition | +move_in_log cost | +1 absence violation | Validate activity scope; may be external |

### 5.2 Non-Recoverable Failures (Cannot Replay)

These indicate fundamental model-log mismatch:

| Failure Type | Indicator | Root Cause | Action |
|---|---|---|---|
| **Deadlock** | TBR fitness = 0; missing tokens > log size | Transition unreachable; circular dependency | Revise model; check for cycles |
| **Complete Divergence** | Alignment cost = 2 × \|σ\|; all moves are deviations | Model and log are unrelated | Discover new model from log |
| **Object Violation** | OCEL conformance = 0; objects have no valid transitions | Object state machine violated | Validate object lifecycle; enforce causality |
| **Constraint Contradiction** | Declare violations on all traces | Constraints are inconsistent | Relax/remove conflicting constraints |

## 6. OCEL-Specific Conformance Details

### 6.1 Object Lifecycle Validation

**Current Limitation:** PM4Py OCEL conformance does NOT validate object state machines. An object can:
- Be created multiple times
- Transition to invalid states
- Lack required transitions for completion

**Workaround:** 
1. Discover OCPN (Object-Centric Petri Net) per object type
2. Use TBR on each object's net separately
3. Validate object interactions via OTG (Object-To-Object Graph) conformance

### 6.2 Event-Object Relation Conformance

**Function:** `conformance_etot(ocel, etot_model)`

Checks:
- Each event is linked to expected object types
- No spurious object-event links
- Required object types always present

**Failure Mode:** If an event can link to >1 object type (ambiguous relations), conformance may overfit.

### 6.3 Object Interaction Conformance

**Function:** `conformance_otg(ocel, otg_model)`

Checks object-type-to-object-type transitions (e.g., Order → Invoice).

**Limitation:** No validation of **temporal ordering** between object interactions. Two objects may interact in either order.

## 7. Alignment Algorithm Variants

PM4Py supports multiple alignment solvers; choice affects both speed and optimality:

| Variant | Algorithm | Optimality | Speed | Best For |
|---------|-----------|-----------|-------|----------|
| `dijkstra_no_heuristic` | A* with reachability | Optimal | Medium | Balanced (default) |
| `dijkstra` | Plain A* | Optimal | Slow | Small nets (<100 transitions) |
| `state_equation_a_star` | State equation heuristic | Optimal | Fast | Nets with few implicit places |
| `twf` | Transfer-follow | Approximate | Very fast | Large, simple nets |

**Selection Rule:**
- Default to `dijkstra_no_heuristic` (reachability heuristic is effective)
- If timeout: switch to `state_equation_a_star` (faster heuristic)
- If still slow: use TBR instead (linear complexity)

---

## 8. Cross-Method Consistency Checks

When applying multiple conformance methods, expect:

**Rule 1: TBR ≥ Alignment Fitness**
- TBR is more permissive; alignment finds cost-optimal deviations
- If reversed: investigate alignment state explosion or suboptimal solution

**Rule 2: Precision (Alignment) ≤ Footprints Precision**
- Footprints are coarse; alignment is fine-grained
- If reversed: footprints missing some edges

**Rule 3: Declare Violations ≤ Alignment Deviations**
- Declare checks specific constraint classes
- If declare violations = 0 but alignment fitness < 0.9: hidden violations not covered by constraints

**Rule 4: OCEL Fitness ≤ Flattened Log Fitness**
- Flattening OCEL loses object-centric structure
- OCEL conformance should be more strict

## 9. Parameters & Variant Selection

### 9.1 Standard Configuration

```python
# Multi-method conformance
net, im, fm = pm4py.convert_to_petri_net(tree)

# Token-Based Replay (fast baseline)
tbr_fitness = pm4py.fitness_token_based_replay(log, net, im, fm)

# Alignment (precise cost)
align_fitness = pm4py.fitness_alignments(log, net, im, fm)
precision = pm4py.precision_alignments(log, net, im, fm)

# Footprints (validation)
footprint_fitness = pm4py.fitness_footprints(log, net, im, fm)

# Temporal (SLA check)
temporal_profile = pm4py.discover_temporal_profile(log)
temporal_dev = pm4py.conformance_temporal_profile(log, temporal_profile, zeta=2.0)

# Diagnostics
diag_align = pm4py.conformance_diagnostics_alignments(log, net, im, fm)
diag_tbr = pm4py.conformance_diagnostics_token_based_replay(log, net, im, fm)
```

## 10. Integration with SPARC Stack

### 10.1 PM4Py as Oracle Baseline

PM4Py is the **reference implementation** for:
- **Conformance Authority:** All other tools (wasm4pm, CodeManufactory) must match or exceed its capabilities
- **Token Replay:** TBR is the classical algorithm; wasm4pm/CodeManufactory must implement equivalent
- **Alignment:** Cost-optimal alignment is the oracle for precision measurement
- **Precision Metric:** Alignment-based precision is authoritative

### 10.2 Limitations vs. wasm4pm

| Dimension | PM4Py | wasm4pm | CodeManufactory |
|-----------|-------|---------|-----------------|
| **Real-Time Conformance** | Batch only (post-hoc) | Streaming (continuous) | Proactive (predictive) |
| **Object Lifecycle** | Structural, no state validation | State machine enforcement | Full causality + proof |
| **Distributed Traces** | Assumes single server | OTel-aware, event correlations | Mesh-aware, AGI-coordinated |
| **Conformance Proof** | Cost metric only | Cryptographic receipt | Proof-of-actuation |
| **Adaptability** | Static model | Variant-aware mutations | Adversarial learning |

### 10.3 Van der Aalst's Constitution

> **"If the code says it worked but the event log cannot prove a lawful process happened, then it did not work."**

**Application to PM4Py Conformance:**
- A model may pass fitness = 0.95 but still violate implicit constraints
- Alignment cost alone is insufficient; must validate:
  1. Event log is authentic (not tampered)
  2. Timestamps are monotonic (no clock skew)
  3. Object lifecycles are valid (no invalid state transitions)
  4. Receipt is cryptographically signed (wasm4pm)/proof-based (CodeManufactory)

## 11. Conformance Testing: Negative Test Cases

### 11.1 Injected Failures (Adversarial Validation)

To verify that PM4Py conformance is not giving **false positives**, inject these impossible traces and confirm rejection:

**Test 1: Activity Not in Model**
```json
{
  "case_id": "test_001",
  "events": ["Register", "HACK_Activity", "Approve", "Ship"]
}
```
**Expected:** TBR fitness ≈ 0.75 (1 move in log), alignment fitness ≈ 0.83

**Test 2: Reverse Order**
```json
{
  "case_id": "test_002",
  "events": ["Ship", "Approve", "Register"]
}
```
**Expected:** Both fitness metrics < 0.5; significant alignment cost

**Test 3: Duplicate Activity (Rework)**
```json
{
  "case_id": "test_003",
  "events": ["Register", "Approve", "Register", "Ship"]
}
```
**Expected:** TBR injection if net disallows loops; alignment cost = +2 for duplicate

**Test 4: Missing Critical Activity**
```json
{
  "case_id": "test_004",
  "events": ["Register", "Ship"]  // Skipped Approve
}
```
**Expected:** TBR missing tokens > 0; alignment cost > log size

### 11.2 Acceptance Thresholds

| Fitness Range | Decision | Confidence |
|---|---|---|
| 0.95-1.0 | Accept | High (lawful process) |
| 0.85-0.94 | Accept with investigation | Medium (minor deviations OK) |
| 0.70-0.84 | Reject unless justified | Low (significant deviations) |
| <0.70 | Reject outright | Fail (non-conformant) |

**Justifications for <0.95:**
- Log contains rare variants (noise threshold filtering justified)
- Process has flexible paths (model is under-constrained)
- Timing variability is expected (SLA bands, not strict bounds)
