## Cross-Boundary Projects

Three projects carry a Supporting Gate (spanning three gate assignments). Each case is explained below.

### ggen — Dung Gate / Inspection Gate / Fountain Gate

ggen is a 15-crate Rust workspace manufacturing RDF-to-code artifacts (TTL → SPARQL → TERA templates → output). The Fountain Gate (source origin) applies because all code generation must trace back to lawful RDF source surfaces — ggen does not merely transform data, it originates artifacts from authoritative ontology sources. This requires a three-gate span: Dung Gate (waste/unlawful surface removal), Inspection Gate (conformance of generated artifacts), and Fountain Gate (source origin accountability).

### Prompt Manufactory — Water Gate / Old Gate / Inspection Gate

The Prompt Manufactory sits at the intersection of three lifecycle concerns: it governs the flow of research intent into downstream subagent directives (Water Gate — governed passage of information), it enforces maturity checkpoints on those directives before release (Old Gate — maturity verification), and it requires conformance inspection of the manufactured prompts themselves (Inspection Gate). Because it is a meta-manufacturing layer that produces prompts consumed by other projects, it inherits gate obligations from both the source domain and the target domain.

### wasm4pm-compat — Horse Gate / Old Gate / Inspection Gate

wasm4pm-compat manages type law across a compile-fail/pass boundary. The Horse Gate applies because it governs motion of types between the compat layer and the wasm4pm execution boundary. The Old Gate applies because graduation from compat to wasm4pm requires maturity verification — only receipted, conformant types may graduate. The Inspection Gate applies because the compile-fail receipt suite itself must be inspected for completeness and correctness. The three-gate span reflects the gatekeeper role of wasm4pm-compat in the broader execution supply chain.

### Living LSP / GALL / CodeManufactory — Inspection Gate / Dung Gate / Water Gate

Living LSP / GALL / CodeManufactory spans three gates because it operates as a lifecycle diagnostic layer over active codebases. The Inspection Gate is primary — all diagnostics must produce inspectable, receipted evidence. The Dung Gate applies because the system must identify and route unlawful, stale, or dead code artifacts for removal. The Water Gate applies because the system governs the passage of lifecycle state information to downstream consumers. This three-gate span reflects the cross-cutting diagnostic authority of the project over multiple downstream projects.
