# tsify / wasm-bindgen Capability Map
## WebAssembly ABI Boundary Law for Ggen Manufacturing
### Document ID: GGEN_ECOSYSTEM_INTEL_002

This document details the capabilities, compile-time mechanics, and runtime behaviors of **tsify**, **wasm-bindgen**, and **wasm-pack** when serving as the JS/Browser ABI crossing lane for `wasm4pm-compat`.

---

## 1. Prime Directive

> **tsify + wasm-bindgen own the WASM ABI surface. They pass pointers and rich memory blocks, never execution tools.**

While Specta defines compile-time TypeScript signatures for our APIs, `tsify` and `wasm-bindgen` work in tandem to marshal values across the WebAssembly linear memory boundary. Execution logic (such as A* search solvers, simulation, queries, or miners) must be completely stripped out of this layer and graduate downstream to the `wasm4pm` engine.

---

## 2. Core Tooling Surface Roles

```
 ┌────────────────────────────────────────────────────────┐
 │                      RUST CRATE                        │
 │  (Provides structs, enums, & FFI entrypoint functions) │
 └───────────────────────────┬────────────────────────────┘
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
 ┌──────────────────────┐         ┌──────────────────────┐
 │     tsify macro      │         │ wasm-bindgen macros  │
 │ (Type Representation)│         │ (Function / Class)   │
 ├──────────────────────┤         ├──────────────────────┤
 │ Parsed via Serde.    │         │ Bridges functions,   │
 │ Generates custom TS  │         │ pointers, and direct │
 │ definition blocks.   │         │ primitive crossings. │
 └──────────┬───────────┘         └───────────┬──────────┘
            │                                 │
            └────────────────┬────────────────┘
                             ▼
 ┌────────────────────────────────────────────────────────┐
 │                    wasm-pack BUILD                     │
 │ (Compiles WASM, runs binder CLI, generates npm package)│
 └───────────────────────────┬────────────────────────────┘
                             │
                             ▼
 ┌────────────────────────────────────────────────────────┐
 │                      pkg/ OUTPUT                       │
 │    (.js wrappers, .wasm binary, and unified .d.ts)     │
 └────────────────────────────────────────────────────────┘
```

1. **wasm-bindgen**: Operates at the lowest level of the FFI. It creates the actual C-style imports and exports, allocates memory on the WASM heap, converts JavaScript strings to Rust string slices, and manages the lifecycle of pointers pointing back to Rust-allocated objects.
2. **tsify**: An ergonomic abstraction built on top of `wasm-bindgen` and `serde`. Instead of forcing developers to wrap every struct in a heavy `wasm-bindgen` class or manually write custom TypeScript sections, `tsify` automatically inspects the Serde attributes on Rust types and emits matching TypeScript interface declarations.
3. **wasm-pack**: The orchestrator. It executes `cargo build` targeting `wasm32-unknown-unknown`, runs the `wasm-bindgen` CLI tool to post-process the binary, extracts custom TypeScript sections generated by `tsify`, and produces a standardized npm package ready for browser deployment.

## 3. Rust-to-TypeScript Mapping Laws

`tsify` supports a wide array of Rust language features, mapping them to precise TypeScript declarations:

### 3.1. Structs
Rust structs map directly to TypeScript interface definitions.
```rust
#[derive(Serialize, Deserialize, tsify::Tsify)]
#[tsify(into_wasm_abi, from_wasm_abi)]
pub struct WitnessKey {
    pub key: String,
    pub index: u32,
    pub active: bool,
}
```
Generates the following `.d.ts` declaration:
```typescript
export interface WitnessKey {
    key: string;
    index: number;
    active: boolean;
}
```

### 3.2. Structs with Optionals & Collections
- `Option<T>` is mapped to `T | null` or `T | undefined` depending on Serde annotations.
- `Vec<T>` maps to `T[]` (unless it is `Vec<u8>`, which maps directly to `Uint8Array` for efficiency).
- `HashMap<String, V>` maps to `Record<string, V>`.

```rust
#[derive(Serialize, Deserialize, tsify::Tsify)]
#[tsify(into_wasm_abi, from_wasm_abi)]
pub struct EvidenceDto {
    pub value: String,
    pub state_tag: String,
    pub witness_key: Option<String>,
    pub metadata: std::collections::HashMap<String, String>,
}
```
Generates:
```typescript
export interface EvidenceDto {
    value: string;
    state_tag: string;
    witness_key: string | null;
    metadata: Record<string, string>;
}
```

### 3.3. Enums (Serde Tagging Styles)
`tsify` honors all Serde enum tagging styles:
*   **Unit Enums**: Map directly to TypeScript string unions.
*   **Externally Tagged (Default)**: Maps to a union of objects, where the key is the variant name.
*   **Internally Tagged**: Maps to a union of objects with a shared discriminator field (e.g. `type`).
*   **Adjacently Tagged**: Maps to objects with separate `type` and `payload` fields.

```rust
#[derive(Serialize, Deserialize, tsify::Tsify)]
#[tsify(into_wasm_abi, from_wasm_abi)]
#[serde(tag = "status", content = "payload")] // Adjacent tagging
pub enum AdmissionResult {
    Admitted(AdmissionDto),
    Refused {
        reason: String,
        rule_violation: String,
    },
}
```
Generates:
```typescript
export type AdmissionResult = 
    | { status: "Admitted"; payload: AdmissionDto }
    | { status: "Refused"; payload: { reason: string; rule_violation: string } };
```

### 3.4. Crate Type Customizations
You can override types using `#[tsify(type = "CustomType")]` when mapping external crate types that do not implement `Tsify` themselves.

## 4. Under-The-Hood Compile-Time Mechanics

The integration between `tsify` and `wasm-bindgen` occurs in two main phases:

### 4.1. Compile Time (Macro Expansion)
When the Rust compiler processes `#[derive(tsify::Tsify)]`:
1. The macro inspects the struct/enum structure and its `#[serde]` attributes.
2. It generates a TypeScript string representation of the type.
3. It emits a `#[wasm_bindgen(typescript_custom_section)]` containing this string:
   ```rust
   #[wasm_bindgen(typescript_custom_section)]
   const TS_APPEND: &'static str = "export interface WitnessKey { key: string; index: number; active: boolean; }";
   ```
4. It implements the `tsify::Tsify` trait for the type, which registers the type's layout.
5. If `#[tsify(into_wasm_abi)]` is declared, it generates the FFI glue allowing direct transfer of the type:
   ```rust
   impl wasm_bindgen::convert::IntoWasmAbi for WitnessKey {
       type Abi = <wasm_bindgen::JsValue as wasm_bindgen::convert::IntoWasmAbi>::Abi;
       fn into_wasm_abi(self) -> Self::Abi {
           let js_val = serde_wasm_bindgen::to_value(&self).unwrap();
           js_val.into_wasm_abi()
       }
   }
   ```
6. If `#[tsify(from_wasm_abi)]` is declared, it generates the corresponding `FromWasmAbi` implementation:
   ```rust
   impl wasm_bindgen::convert::FromWasmAbi for WitnessKey {
       type Abi = <wasm_bindgen::JsValue as wasm_bindgen::convert::FromWasmAbi>::Abi;
       unsafe fn from_wasm_abi(js_val: Self::Abi) -> Self {
           let val = wasm_bindgen::JsValue::from_wasm_abi(js_val);
           serde_wasm_bindgen::from_value(val).unwrap()
       }
   }
   ```

### 4.2. Bindgen Extraction Phase (`wasm-pack`)
During the post-processing phase:
1. `wasm-bindgen` parses the compiled `wasm32-unknown-unknown` binary.
2. It finds all `typescript_custom_section` metadata blocks embedded in the WASM module.
3. It copies these blocks word-for-word into the output `pkg/index.d.ts` file.
4. It generates TypeScript signatures for exported `#[wasm_bindgen]` functions, automatically substituting types implementing `Tsify` with their TypeScript counterparts instead of generic `any` or `number` pointers.

## 5. Performance, Memory, and Garbage Collection Profiles

When designing boundary crossings, choose the correct marshaling strategy based on performance characteristics:

| Criterion | `wasm-bindgen` Class Pointer | `tsify` (Serde-Wasm-Bindgen) |
| :--- | :--- | :--- |
| **Data Layout** | Rust memory heap allocation | Serialized Javascript Object |
| **Crossing Overhead** | Zero-copy (Passes a `u32` pointer) | Medium (Serialization to `JsValue`) |
| **Access Latency** | High (JS calls getter functions via FFI) | Zero (Native JS field lookup) |
| **Memory Management** | Manual (Must call `.free()` in JS) | Automatic (Garbage collected by JS Engine) |
| **Complexity** | High (Requires wrappers/lifetimes) | Low (Plain Data Transfer Objects) |

### 5.1. The Memory Leak Hazard
When using raw `#[wasm_bindgen]` structs:
```rust
#[wasm_bindgen]
pub struct ActiveSolver {
    state: Vec<u8>,
}
```
This allocates memory on the WASM linear memory heap. If JavaScript instantiated this class:
```javascript
const solver = new ActiveSolver();
// ... usage
// If the developer forgets to call:
solver.free();
```
The memory is leaked forever.
In contrast, `tsify` outputs plain JS objects. Once JavaScript is done with the object, the JS engine's garbage collector reclaims the memory automatically, preventing linear memory bloating.

## 6. Packaging Workflow (`wasm-pack`)

To prepare the `wasm4pm-compat` crate for integration, `wasm-pack` is executed using the following structure:

```bash
wasm-pack build --target bundler --out-dir pkg/browser
```

### 6.1. Package Targets
- `--target bundler`: Optimized for modern bundlers like Webpack, Vite, or Rollup. Automatically handles asynchronous loading of the WASM module.
- `--target web`: Intended for direct browser loading using ES Modules without a build tool.
- `--target nodejs`: Compiles the bindings to use CommonJS `require` statements, ideal for server-side testing.

### 6.2. Package Manifest (`package.json`)
The generated `pkg/package.json` contains:
- `name`: Crate name (e.g. `wasm4pm-compat`).
- `collaborators` & `version` cloned from Cargo.toml.
- `main` and `module` fields pointing to the generated Javascript wrapper file.
- `types` field pointing to the generated `.d.ts` typescript declaration.
- `files` array listing the required release assets (`wasm`, `js`, `d.ts`).
