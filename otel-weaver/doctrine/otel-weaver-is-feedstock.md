## The Feedstock Theorem

OpenTelemetry semantic conventions and the Weaver framework define the *structure* of observability data. They do not define the *consequence* of execution. 

The core error of telemetry-heavy architectures is the assumption that a structurally correct telemetry payload is equivalent to a valid process state. The Feedstock Theorem refutes this:

$$\text{Telemetry} \in \text{Feedstock}$$
$$\text{SchemaValidation}(\text{Telemetry}) \neq \text{ProcessCompliance}(\text{ProcessState})$$

Structural alignment is merely the verification that our instruments are recording within expected parameters. It is an engineering metric. Process compliance, by contrast, is a legal and operational assertion that requires type law enforcement, execution replay, and receipt-backed witness verification.

---

## Schema Validation vs. Conformance Checking

We must maintain a strict nominal boundary between two distinct operations:

| Attribute | Schema Validation (OTel Weaver) | Conformance Checking (Process Intelligence) |
| :--- | :--- | :--- |
| **Object of Analysis** | Telemetry payload (json, protobuf, yaml) | Reconstructed event log vs. normative process model |
| **Verification Level** | Syntactic and structural (attribute presence, type checks) | Semantic and temporal (activity ordering, object linkages, token replay) |
| **Authority** | Systems/Infrastructure | Board Room / Legal Court / Compliance Registry |
| **Failure Mode** | Invalid payload (rejected by collector) | Unlawful process transition (raises conformance exception) |
| **Output** | Validated span payload | Conformance Receipt or Exception Log |

If a span representing `dispatch_payment` passes OTel Weaver validation (meaning it contains `payment.amount`, `payment.currency`, and `payment.recipient.id`), it is **validated feedstock**. 

However, if that payment was dispatched *before* the credit check was completed, the execution violates the normative business model ($A \to B$ sequence constraint). Weaver has no concept of this temporal and causal relation; it only knows that the span's internal keys are populated. The feedstock is structurally clean, but the process is non-conforming.

## Why OTel Weaver is Feedstock

OTel Weaver is feedstock because it resides outside the boundary of Process Consequence. 

1. **Passive Observation**: Telemetry is generated by passive instrumentation. The telemetry collector does not actuate the system or block unlawful state transitions; it merely records them.
2. **Lossy Projection**: The mapping from distributed spans to object-centric event logs is lossy. Span duration is simplified, context is stripped, and parent-child trace references are correlation markers rather than strict process causality relationships.
3. **No Execution Authority**: Weaver cannot emit a receipt that survives audit. It can say, "This log is a valid JSON schema." It cannot say, "This transaction was executed in accordance with the regulatory delegation of authority."

---

## The Ingestion Covenant

To ensure telemetry feedstock is safely processed without laundering bad data, all systems must adhere to the Ingestion Covenant:

1. **Admit, Don't Assume**: Telemetry must not enter the execution path directly. It must be explicitly ingested via the `Admit` boundary, which maps OTel trace spans to `OcelEvent` structures using verified projections.
2. **Loss Reports**: Every projection of telemetry must generate a `LossReport`. If we project a trace containing 500 microsecond-level spans into 5 key activity events, the lost spans must be accounted for and sealed with a `LossReport` receipt.
3. **Witness Seal**: The transformation from OTel telemetry to process events must be sealed with a zero-sized witness type, such as `OtelSpanToOcelEventProjection`. This ensures the translation logic can be replayed and audited independently.
