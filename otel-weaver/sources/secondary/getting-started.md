# Getting Started with OpenTelemetry Weaver

Welcome! This guide is designed to get you up and running with **OpenTelemetry Weaver** (`otel-weaver`) in less than 15 minutes. We will cover installing the CLI, structuring a basic registry, checking it against policy rules, generating code, and conducting a live telemetry check.

---

## 1. Concepts and Terminology

Before we write code, it is vital to understand the vocabulary and data flow of Weaver in our process intelligence landscape:

1.  **Telemetry is Feedstock**: Raw traces, spans, and metrics are the feedstock. They are raw data feeds that must be cleaned, structured, and validated.
2.  **Process Consequence is Court**: Downstream compliance checking, SLA auditing, and process intelligence calculations are the court. They require certified data to produce admissible evidence.
3.  **Weaver Diffs are not Process Drift**: Comparing schemas using `weaver registry diff` tells you if your *telemetry contracts* have changed (static schema evolution). This is completely distinct from *process drift*, which is runtime deviation in system activity flow paths or latency.

## 2. Installation

You can build and install Weaver directly from the source code.

### Prerequisites
*   Ensure the [Rust Toolchain](https://rustup.rs/) is installed on your computer.

### Build Steps
```bash
# 1. Clone the repository
git clone https://github.com/open-telemetry/weaver.git
cd weaver

# 2. Compile and install CLI
cargo install --path crates/weaver_cli

# 3. Verify the installation
weaver --version
```
*Expected Output*: `weaver 0.22.1`

## 3. Step-by-Step Setup Tutorial

### Step 3.1: Initialize the Registry
Create a new directory to house your organization's telemetry registry contract:
```bash
mkdir -p my-telemetry-contract/groups
cd my-telemetry-contract
```

Create a root `manifest.yaml` configuration file to define your metadata and import the official OpenTelemetry semantic conventions:
```yaml
# manifest.yaml
name: "corp-telemetry-schema"
description: "Core Telemetry Schemas for Corporate Microservices"
schema_url: "https://opentelemetry.io/schemas/1.25.0"
dependencies:
  - name: "semconv"
    registry_path: "https://github.com/open-telemetry/semantic-conventions.git@v1.25.0[model]"
```

Now, define your first custom attribute group for application metadata. Create `groups/app.yaml`:
```yaml
# groups/app.yaml
file_format: "definition/2"
groups:
  - id: corp.app
    type: attribute_group
    brief: "Attributes identifying corporate application execution units."
    prefix: corp.app
    attributes:
      - id: service_tier
        type: string
        brief: "The business critical rating of the microservice (e.g. tier-1, tier-2)."
        stability: stable
        requirement_level: required
        examples: ["tier-1", "tier-2", "tier-3"]
```

---

### Step 3.2: Verify and Lint the Registry
Ensure your registry compiles and follows rules by validating it:
```bash
weaver registry check --registry . --future
```
If it displays no errors, your telemetry contract is syntactically sound.

---

### Step 3.3: Write a Policy to Enforce Standards
Create a policy file `./policies/tier_naming.rego` to guarantee that all custom attributes are cataloged with the `corp.` prefix:
```rego
package weaver

deny[msg] {
	attr := input.attributes[_]
	not startswith(attr.id, "corp.")
	not startswith(attr.id, "semconv.") # Allow imported standard conventions
	msg := sprintf("Validation Error: Custom attribute '%s' must begin with 'corp.' namespace", [attr.id])
}
```

Now execute the validator including the policy:
```bash
weaver registry check --registry . --policy ./policies
```

---

### Step 3.4: Generate Code Artifacts
Weaver generates telemetry constants so developers don't have to copy-paste string keys.

Create a templates folder `./templates/go` and add the following `weaver.yaml` file:
```yaml
# templates/go/weaver.yaml
whitespace_control:
  trim_blocks: true
  lstrip_blocks: true

text_maps:
  go_types:
    string: "string"

comment_formats:
  go_doc:
    format: text
    prefix: "// "
    trim: true

params:
  package_name: "telemetry"

templates:
  - template: "constants.go.j2"
    filter: ".groups[] | select(.type == \"attribute_group\")"
    application_mode: each
    output_path: "attributes_{{ group.id | replace(\"corp.\", \"\") }}.go"
```

Create `./templates/go/constants.go.j2`:
```jinja2
// Code generated by OpenTelemetry Weaver. DO NOT EDIT.
package {{ params.package_name }}

const (
	{%- for attr in group.attributes %}
	// {{ attr.brief | comment("go_doc") }}
	{{ group.id | replace(".", "_") | upper }}_{{ attr.id | replace(".", "_") | upper }} = "{{ group.prefix }}.{{ attr.id }}"
	{%- endfor %}
)
```

Generate the code:
```bash
weaver registry generate \
  --registry . \
  --templates ./templates/go \
  go ./output/go
```
Check `./output/go/attributes_app.go` to inspect the generated code constants!

---

### Step 3.5: Run a Live-Check Verification
To verify that your microservices actually emit the required `corp.app.service_tier` attribute at runtime, spin up `live-check`:
```bash
weaver registry live-check \
  --registry . \
  --otlp-grpc-port 4317 \
  --inactivity-timeout 20 \
  --format json \
  -o ./live-report.json
```
Point your microservices' OTel exporter endpoint to `http://localhost:4317`. If any microservice sends spans missing the `corp.app.service_tier` attribute, they will be cataloged in the generated `./live-report.json` file. This prevents invalid feedstock from corrupting downstream compliance analysis.
