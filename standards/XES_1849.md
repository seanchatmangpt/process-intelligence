# XES IEEE 1849 — eXtensible Event Stream Standard

**Authority:** IEEE Std 1849-2016 (XES)
**Witness key:** `xes-1849` — `WitnessFamily::Standard`

---

## Standard Overview

XES (eXtensible Event Stream) is the IEEE 1849 interchange format for case-centric event
logs. It is emphatically **not** object-centric: every event belongs to exactly one trace,
every trace belongs to exactly one log. This case-centric assumption is the defining
boundary between XES and OCEL 2.0.

### Four Core Structural Objects

| XES object | Description |
|---|---|
| **Log** | Root container; declares global attributes and registered extensions. |
| **Trace** | A sequence of events sharing a single case notion (case ID). |
| **Event** | A timestamped activity occurrence within a trace, carrying typed attributes. |
| **Attribute** | A typed key/value pair (string, int, float, boolean, timestamp, list, container). |

### Standard Extensions

XES extensions namespace attributes under well-known prefixes:

| Extension | Prefix | Key attributes |
|---|---|---|
| Concept | `concept:` | `concept:name` — the activity name |
| Time | `time:` | `time:timestamp` — event timestamp |
| Lifecycle | `lifecycle:` | `lifecycle:transition` — `start`, `complete`, etc. |
| Org | `org:` | `org:resource`, `org:role`, `org:group` |

## wasm4pm-compat Implementation (xes.rs)

`src/xes.rs` models XES as the **concrete interchange** canon (where `eventlog.rs` is the
abstract case-centric canon):

- `XesLog` — declares `extensions: Vec<XesExtension>`, global attributes, and traces.
- `XesTrace` — a list of `XesEvent`s under a case identifier.
- `XesEvent` — carries `concept:name`, `time:timestamp`, optional `lifecycle:transition`,
  and arbitrary extension attributes.
- `XesExtension` — records `name`, `prefix`, `uri` for each declared extension.
- `CaseCentricMarker` — a zero-sized `PhantomData` tag that prevents, at the type level,
  confusing a case-centric log shape with `OcelLog`.
- `XesLog::validate()` — structural shape check: required interchange keys present,
  extensions well-formed. Does not parse a `.xes` file (that is an import engine).

## Loss Policy: OCEL → XES Projection

Projecting OCEL 2.0 to XES is lossy by construction. The laws:

1. OCEL has multiple object types; XES has one case notion. Projecting requires choosing
   (or merging) a case notion — this discards convergence/divergence information.
2. O2O links have no XES representation — they are silently dropped unless explicitly
   named in a `LossReport`.
3. ObjectAttributeChange history has no XES representation — change history is dropped.

These losses are not discrepancies. They are defects unless named:

- A projection must declare a `ProjectionName` (e.g. `"ocel-to-xes-case-order"`).
- It must choose a `LossPolicy`: `RefuseLoss` rejects the projection; `AllowNamedProjection`
  permits it with a name; `AllowLossWithReport` permits it and emits a `LossReport`.
- The `LossReport` records which object types, O2O links, and change records were
  discarded — so a downstream consumer knows exactly what was lost.

See `examples/ocel_to_xes_projection` for the full covenant in action.

## Board Placement

XES IEEE 1849 is the universal interchange format for process mining tool chains (pm4py,
ProM, Celonis, Disco). A wasm4pm stack that cannot read or write XES cannot interoperate
with any existing process mining ecosystem. The loss covenant in wasm4pm-compat ensures
that projection from OCEL 2.0 to XES always carries a named `LossReport` — so the board
can audit what was discarded in any XES export.
