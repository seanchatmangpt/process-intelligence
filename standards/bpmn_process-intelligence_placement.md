# BPMN Standard Ledger Placement

The **Business Process Model and Notation (BPMN 2.0)** (Weske 2019) is the industry standard for graphical process modeling. While BPMN focuses on visualization, the Process Intelligence Research Foundry maps BPMN structures to formal execution semantics (Petri nets) to enable mathematical validation. This document defines how BPMN models are registered, verified, and mapped on the ledger.

---

## 1. Ontological Mapping to the Ledger

BPMN flow elements are mapped directly to places and transitions in the ledger's semantic representation:

| BPMN Flow Element | Petri Net Translation | Ledger Class | Description |
| :--- | :--- | :--- | :--- |
| **Start Event** | Source Place ($i$) | `ProcessEntryPlace` | The initialization node for a process instance case. |
| **Task / Activity** | Transition ($t$) | `ProcessTaskTransition` | An executable activity representing a state change. |
| **Sequence Flow** | Directed Arc ($F$) | `ProcessControlFlowArc` | Defines execution order and token routing. |
| **Exclusive Gateway (XOR Split)** | Choice Place / Transitions | `ProcessXORSplit` | Routes a token to exactly one of the outgoing branches. |
| **Parallel Gateway (AND Split)**| Fork Transitions | `ProcessANDSplit` | Generates tokens in all parallel outgoing branches. |
| **Inclusive Gateway (OR Split)** | Complex routing subnets | `ProcessORSplit` | Routes tokens to one or more branches. |
| **End Event** | Sink Place ($o$) | `ProcessExitPlace` | The termination node of the process instance. |

## 2. Structural and Execution Type Laws

To prevent deadlocks and execution leakage, any BPMN model registered on the ledger must satisfy structural properties:

1.  **Structured Gateway Pairing**: For every divergence gateway (Split), there must be a matching convergence gateway (Join) of the same type, unless the process structure can be proven sound via state space exploration.
2.  **Soundness Constraint**: The translated Petri Net must be structurally sound (van der Aalst 1998):
    *   **Liveness**: No tasks are dead; every task is reachable.
    *   **Boundedness**: No infinite queue accumulation (1-boundedness of control places).
    *   **Option to Complete**: The process can always reach the End Event.
3.  **Cryptographic Blueprint**: The BPMN XML source is hashed and linked to its Petri Net equivalent:
    $$\mathcal{H}_{\text{BPMN}} = \operatorname{BLAKE3}\left( \text{BPMN\_XML} \parallel \text{PetriNet\_Translation} \right)$$

## 5. Trans-Standard Conversions and Loss Policy

### 5.1 Conversion: BPMN 2.0 to Petri Net (Sound Compilation)
When compiling a BPMN 2.0 model to a mathematically verified Petri Net, the compiler maps sequence flows and gateway splits/joins to bipartite structures of places and transitions.

*   **Structural Loss Policy**:
    1.  **Gateway Simplification & Expansion**: Standard BPMN AND/XOR gateways map cleanly. Inclusive (OR) splits/joins require expansion into complex Petri Net sub-structures representing all possible token subsets. If the OR-join logic cannot be resolved statically to guarantee liveness, compilation is refused.
    2.  **Pruning of Non-Execution Semantics**: Message flows, association links, pools, lanes, data objects, and text annotations are completely discarded during Petri Net generation.
    3.  **Boundary Exception Pruning**: Boundary interrupt events (e.g., timers or errors) are flattened into standard choice routing transitions, losing the hierarchical task-interruption semantics.
*   **Signed LossReport Output Schema**:
    Every compilation generates a `LossReport` signed by the compiler witness:
