## 1. Executive Summary

This report presents a formal, mathematically rigorous comparison of the core process mining algorithms—**Alpha Miner (AM)**, **Heuristics Miner (HM)**, and **Inductive Miner (IM)**—as mapped in the legacy Python-based [Capability Atlas](file:///Users/sac/process-intelligence/sources/pm4py/capability-atlas.md) and the WebAssembly-based [Mining Authority Map](file:///Users/sac/process-intelligence/sources/wasm4pm/mining-authority-map.md).

The comparison focuses on:
1. **Algorithmic Discrepancies:** The shift from legacy, heuristic, or fragile discovery strategies (e.g., Alpha Miner) to formal soundness by construction and structured proofs.
2. **Rejection of Python/Pandas Assumptions:** Deconstructing the performance and security risks of CPython's execution model (GIL, dynamic typing, mutable heap memory, garbage collection, and Pandas dynamic DataFrames) in a high-assurance process intelligence framework.
3. **WASM Execution Model Optimizations:** Detailing the zero-copy, memory-isolated, instruction-metered, and cryptographically attested architecture implemented within `wasm4pm`.

## 2. Core Process Mining Algorithm Comparison

The three core process mining algorithms represent distinct epochs of process discovery research. The transition from PM4Py to `wasm4pm` alters their implementation, guarantees, and constraints.

### 2.1 The Alpha Miner (AM)

#### PM4Py Legacy Design
The Alpha Miner is the foundational process discovery algorithm. PM4Py implements it via `discover_petri_net_alpha` and `discover_petri_net_alpha_plus`.
* **Mechanism:** It operates by scanning the log to discover footprints (direct succession $a > b$, causality $a \rightarrow b$, parallel/concurrency $a \parallel b$, and choice $a \mathbin{\#} b$) and then synthesizing a workflow net (WF-net) using maximum sets of cause-effect relationships.
* **Soundness:** It offers no structural soundness guarantees for real-world, noisy logs. Soundness is only guaranteed if the event log is generated by a sound structured workflow net, contains no missing transitions, and represents all possible paths (retrospective completeness).
* **Python/Pandas Overhead:** Relies on flat scanning of traces. Pandas data structures must be scanned to find unique transition pairs, incurring $O(|L| \cdot \bar{t} + |A|^2)$ complexity where $|L|$ is trace count, $\bar{t}$ is average trace length, and $|A|$ is activity alphabet size.

#### wasm4pm Execution Model Status
* **Classification:** Explicitly **omitted** from the mandatory implementation paths of the [Mining Authority Map](file:///Users/sac/process-intelligence/sources/wasm4pm/mining-authority-map.md).
* **Rationale:** The Alpha Miner violates Van der Aalst's Constitution ("If the code says it worked but the event log cannot prove a lawful process happened, then it did not work"). Because AM cannot handle noise, produces unsound nets on incomplete logs, and has no capacity for error-recovery, it is excluded from high-assurance runtime admission.
* **Attestation:** The engine supports importing third-party Alpha-mined models, but they must undergo post-hoc soundness audits via the [Replay Authority Map](file:///Users/sac/process-intelligence/sources/wasm4pm/replay-authority-map.md) and carry an external `alpha-miner` origin receipt.

### 2.2 The Heuristics Miner (HM)

#### PM4Py Legacy Design
PM4Py implements the Heuristics Miner via `discover_heuristics_net`, which discovers a `HeuristicsNet` (C-net) based on frequency thresholds, which is then optionally converted to a Petri net.
* **Mechanism:** HM calculates a dependency measure between activity pairs:
  $$\text{dep}(a, b) = \frac{|a \to b| - |b \to a|}{|a \to b| + |b \to a| + 1}$$
  It uses configurable parameters (`dependency_threshold`, `and_threshold`, `loop_two_threshold`) to filter out noise.
* **Limitations:** It relies on heuristics to infer concurrency and loops. PM4Py's implementation cannot guarantee structural soundness of the resulting Petri Net; it frequently outputs nets with deadlocks or dangling places when converted.

#### wasm4pm Execution Model Status
* **Classification:** **Mandatory Implementation** in the [Mining Authority Map](file:///Users/sac/process-intelligence/sources/wasm4pm/mining-authority-map.md).
* **WASM Optimizations:**
  * **Contiguous Memory Allocation:** The dependency matrix is allocated as a flat, contiguous 2D array in guest linear memory. It requires a hard limit of $|A| \le 1,000$ to prevent quadratic stack/heap exhaustion.
  * **Deterministic Tie-Breaking:** In PM4Py, tie-breaking between equal-weight dependencies is non-deterministic (dependent on Python dict ordering, hash randomization, or pandas index layout). In `wasm4pm`, tie-breaking must use deterministic lexicographical comparison of activity label hashes to ensure execution is identical across architectures.
  * **Loss Attestation:** The resulting `HeuristicsNet` receipt must explicitly calculate and embed a `lost_concurrency_estimate` to quantify information lost when flattening concurrent paths.

### 2.3 The Inductive Miner (IM)

#### PM4Py Legacy Design
PM4Py implements the Inductive Miner family (`im`, `imd`, `imf`, `imc`) via `discover_process_tree_inductive` and `discover_petri_net_inductive`.
* **Mechanism:** IM recursively partitions the event log by detecting cuts in the Directly-Follows Graph (DFG). The cuts correspond to process tree operators: Sequence ($\rightarrow$), Exclusive Choice ($\times$), Concurrent ($\wedge$), and Loop ($\circlearrowleft$). If no cut is found, a fallback (e.g., trace splitting or empty transition insertion) is applied.
* **Soundness:** Soundness is guaranteed by construction because the process tree can always be translated into a sound Workflow Net.
* **Python/Pandas Overhead:** The recursive partitioning requires copying or slicing sub-logs at every node in the recursion tree. Slicing Pandas DataFrames and re-generating DFGs at each recursion depth creates significant dynamic memory overhead and triggers frequent garbage collection passes.

#### wasm4pm Execution Model Status
* **Classification:** **Mandatory Implementation** in the [Mining Authority Map](file:///Users/sac/process-intelligence/sources/wasm4pm/mining-authority-map.md).
* **WASM Optimizations:**
  * **Zero-Copy Sub-DFG Views:** Rather than cloning and partitioning the event log at each recursive cut, `wasm4pm` maintains a single read-only view of the event log and projects sub-DFG cuts as bitmask indices in guest memory.
  * **Recursion Stack Safety:** Rust's memory manager optimizes the recursive call stack. In `wasm4pm`, a stack-depth guard prevents deep recursion limits from causing WASM engine traps.
  * **Cryptographic Block Invariants:** Emits an Ed25519-signed receipt containing a BLAKE3 challenge-response proof-of-work (PoW) witness. This receipt attests to the depth of the process tree, the count of leaf nodes, and the distribution of operators, preventing "raw laundering" of hand-crafted nets.

## 3. Rejection of Python & Pandas Assumptions

High-assurance process intelligence engines cannot rely on CPython and Pandas. The table below outlines the core dynamic assumptions that must be rejected:

| Legacy Python/Pandas Assumption | Operational Risk | `wasm4pm` Architectural Rejection |
| :--- | :--- | :--- |
| **DataFrames as Primary Ingestion** | Columnar tables optimized for relational math but poorly suited for linear graph scanning. Dynamic column types and index alignment add CPU cycles. | Direct event-ordered parsing of XES and OCEL 2.0 binary streams into flat memory arenas. |
| **Dynamic Memory & Garbage Collection** | Large memory footprint (approx. 20-30x the raw log size). GC pauses during deep recursive mining (IM) trigger non-deterministic execution times. | Pre-allocated, zero-copy memory arenas in WASM linear memory. No dynamic heap allocation in the core mining loop. |
| **GIL (Global Interpreter Lock)** | Parallel processing (`multi_processing: bool`) requires serialization of DataFrames and IPC overhead, defeating benefits. | Multi-threading via deterministic WASM threads or host-orchestrated parallel execution pipelines with zero-copy FFI buffers. |
| **Dynamic Typestate Verification** | Models (Petri Nets, Trees) are mutable Python objects. Any step in a script can corrupt the model structure (e.g., adding an orphaned place) without validation. | Compile-time typestate pattern enforcement in Rust. A model cannot transition from `Mined` to `Conformant` without a valid cryptographic signature. |
| **IEEE-754 NaN Coercion** | Missing event log attributes are dynamically coerced to `float64 NaN`, which corrupts activity labels or resource strings. | Strict schema enforcement (OCEL 2.0/XES). Missing values are handled via Rust `Option<T>` or rejected at the boundary. |

## 4. WASM Execution Model Optimizations

The WebAssembly sandbox enforces constraints that `wasm4pm` converts into performance optimizations:

```
┌──────────────────────────────────────────────────────────┐
│              wasm4pm WASM Linear Memory                  │
├──────────────────────────────────────────────────────────┤
│ [0.0 - 1.5 GB]  Event Log Raw Data Arena (Read-Only)      │
│ [1.5 - 2.5 GB]  Model Graph AST & State Space (Mutable)   │
│ [2.5 - 4.0 GB]  Computation Scratch & DFG Bitmasks       │
│ [4.0 - 4.06GB]  Receipt Accumulation & Serialization     │
└──────────────────────────────────────────────────────────┘
```

1. **Static Linear Memory Allocation:**
   * At runtime, `wasm4pm` pre-allocates a contiguous heap (up to 4GB in wasm32).
   * Event logs are parsed directly into the **Event Log Raw Data Arena** as flat byte arrays.
   * Directly-Follows Graphs (DFG) are represented as dense adjacency matrices, avoiding pointer-chasing associated with Python dictionaries.
2. **Instruction Metering & Cycle Budgets:**
   * The WASM runtime JIT engine enforces instruction-level metering.
   * The Inductive Miner has a budget of 5,000,000 cycles, and the Heuristics Miner has a budget of 3,000,000 cycles.
   * If a phase exceeds its budget, it halts with error code `0xFB01` (cycle overflow) and emits a partial refusal report rather than hanging the host thread.
3. **Hardware Trap Safety:**
   * Memory pointer validation is handled at the WASM boundary. Out-of-bounds reads or writes trigger hardware traps rather than silent memory corruption.
4. **Deterministic Graph Construction:**
   * To achieve deterministic outputs across differing CPU architectures (e.g., x86_64 vs. ARM64), all floats (e.g., noise thresholds, dependency measures) are either converted to fixed-point integers or sorted using strict, non-NaN-dependent ordering rules.

## 6. Recommendations & Action Plan

To ensure the high-performance execution of these algorithms in `wasm4pm`, the following implementation tasks must be completed in the next development cycle:

1. **Establish the Zero-Copy DFG Projection Interface:**
   * Build the DFG construction kernel in Rust to operate on raw event slices.
   * Avoid any creation of intermediate `HashMap` structures. Use indexed lookup arrays.
2. **Implement Lexicographical Tie-Breaking:**
   * Enforce that all node and edge sorting algorithms in the DFG and Heuristics Miner utilize the SHA-256 hash of the activity names as the secondary sorting key to guarantee cross-platform determinism.
3. **Rigorous Stack Guarding for Inductive cuts:**
   * Implement the Process Tree decomposition using an iterative, stack-allocated loop rather than native recursion to protect WASM from stack overflow errors during complex discovery phases.
4. **Receipt Chaining Integration:**
   * Bind the generated process tree POWL AST to the hash of the input log in the output JSON receipt, signing the final payload using Ed25519 at the guest-host FFI boundary.
