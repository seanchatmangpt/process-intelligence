\subsection{Contribution to Prediction vs.~Coordination}
\label{sec:otel-weaver-exp-003-live-check-to-refusal-contribution-prediction}

The central thesis argument distinguishes prediction --- the probabilistic modeling
of future states from historical data --- from coordination --- the enforcement of
lawful process execution in real time. EXP-003 contributes a concrete implementation
of the coordination boundary: the telemetry ingestion frontier where raw observations
are either admitted to the coordination layer or refused with an auditable record.

This contribution is mechanistic rather than theoretical. The \texttt{validate\_and\_project}
function does not predict whether a given feedstock is likely to be lawful; it
deterministically enforces whether it is structurally admissible under the named-law
refusal doctrine. Prediction would ask: ``given this stream of spans, what is the
probability that the next span will be compliant?'' Coordination asks: ``is this
span, right now, structurally compatible with admission to the conformance court?''
EXP-003 implements the coordination question as a compile-time type gate.

The doctrine file \texttt{otel-weaver-is-feedstock.md} formalizes the coordination
boundary at the theoretical level: ``Passive Observation: Telemetry is generated by
passive instrumentation. The telemetry collector does not actuate the system or block
unlawful state transitions; it merely records them.'' EXP-003 operationalizes the
complement of this statement: the ingestion gate does actuate --- it blocks unlawful
feedstock from entering the court, converting passive observation into active
coordination. \textbf{(AUTHOR THESIS)}

\subsection{Contribution to Process Evidence}
\label{sec:otel-weaver-exp-003-live-check-to-refusal-contribution-evidence}

EXP-003 contributes to the process-evidence layer by establishing the \texttt{Refusal}
type as a first-class process artifact. In conventional telemetry pipelines, validation
failures produce log entries that are discarded after retention windows expire.
The \texttt{Refusal} struct, by contrast, is a serializable, BLAKE3-digested record
that captures the original feedstock, the violated rule, and a cryptographic fingerprint
of the failure context. It is designed to be archived in a persistent ledger
(\texttt{refusals.json}) and to serve as evidence that the gate operated correctly.

This contribution is grounded in the Van der Aalst Constitution
(\texttt{process-mining-chicago-tdd.md}), which requires that all process lifecycle
events --- including rejections --- be representable as object-centric log entries
that can be mined for conformance. A \texttt{Refusal} record satisfies this requirement:
it has an object (the raw feedstock), a timestamp context (the BLAKE3 digest encodes
the failure state), and a law reference (the \texttt{violated\_rule} string). The
pending gap is the absence of a timestamp field in the current \texttt{Refusal} struct
and the unimplemented \texttt{refusals.json} persistence layer.

The integration test validates the process-evidence quality of the \texttt{Refusal}
type by asserting \texttt{blake3\_digest.len() == 64} across all four failure cases,
confirming that each \texttt{Refusal} carries a genuine cryptographic fingerprint
rather than a placeholder string.

\subsection{Contribution to Manufacturing Architecture}
\label{sec:otel-weaver-exp-003-live-check-to-refusal-contribution-manufacturing}

EXP-003's place in the five-experiment OTel Weaver integration suite establishes a
manufacturing pipeline for telemetry-to-process-evidence projection. The pipeline
is: EXP-001 (custom PI semantic conventions registry) $\rightarrow$ EXP-002 (schema
diff bridge, \texttt{BridgeRx}) $\rightarrow$ EXP-003 (live-check refusal gate)
$\rightarrow$ EXP-004 (registry-to-witness code generator) $\rightarrow$ EXP-005
(collector intake configuration). EXP-003 is the quality gate in this pipeline:
it is the only stage that can halt feedstock flow entirely by emitting a
\texttt{Refusal} rather than passing the feedstock downstream.

The manufacturing architecture contribution is documented in checkpoint
\texttt{GGEN\_OTEL\_WEAVER\_PI\_ALIVE\_001}, which certifies that ``No telemetry
feedstock is allowed into the process mining core unless wrapped inside the
\texttt{Admission<T, W>} structure.'' This invariant is enforced by EXP-003's type
gate. The two \texttt{ggen} templates (\texttt{pi-live-check-intake.rs.ggen} and
\texttt{audit-live-check-findings-routed.sh.ggen}) indicate that the manufacturing
pipeline intends to manufacture the intake and audit code from templates rather than
maintain hand-written source, closing the gap between the prototype
\texttt{validator.rs} and a production-grade manufactured artifact.

\subsection{Contribution to Capital-Flow Infrastructure}
\label{sec:otel-weaver-exp-003-live-check-to-refusal-contribution-capital}

The capital-flow and settlement layers of the thesis lineage require that process
evidence be grounded in receipts that survive legal and financial audit. EXP-003
contributes to this layer by defining the admission precondition: for any process
event to participate in a capital-flow settlement computation, it must have passed
through an admission gate of the form implemented by EXP-003. An event that lacks
a verified witness hash (\texttt{InvalidWitnessSignature}) cannot be admitted and
therefore cannot participate in downstream settlement calculations.

This contribution is at the documentation level as of the current experiment state:
no formal type binding from \texttt{Admission<AdmittedPayload, AlphaWitness>} to
the capital-flow settlement types exists in the current codebase. The checkpoint
prose in \texttt{GGEN\_OTEL\_WEAVER\_PI\_ALIVE\_001} asserts the connection
(``all downstream algorithms \ldots\ only consume elements wrapped in
\texttt{Admission<T, W>}''), but the downstream settlement algorithms are not yet
implemented in the \texttt{wasm4pm} workspace in a form that enforces this
constraint via type bounds. \textbf{(FUTURE WORK: formal type binding from
\texttt{Admission<T,W>} to settlement computation inputs)}
