\section{Evidence, Receipts, and Gates}
\label{sec:standards-evidence}

\subsection{Tests}
\label{sec:standards-evidence-tests}

The standards project maintains three categories of evidence tests, all documented as
named artifacts:

\paragraph{Adversarial vulnerability probes.}
The adversarial test report \texttt{ocel-adversarial-gravity.md} (identifier
OCEL-XES-ADV-V30.1.1) identifies four structural vulnerabilities in XES and OCEL native
formats operating under the old regime:
\begin{enumerate}
  \item \textbf{Phantom-object injection}: Events in an OCEL log bound to object
        identifiers absent from the object set $\mathcal{O}$, exploiting absent structural
        validation.
  \item \textbf{Timeline manipulation}: Out-of-order event timestamps in XES traces
        that pass ingestion without chronological invariance enforcement.
  \item \textbf{Hash-chain paradox}: A receipt that claims hash-chain integrity while the
        underlying event sequence has been modified, because the hashing is performed on
        attributes rather than the full event record.
  \item \textbf{Cryptographic tombstone deficiencies}: XES logs containing PII-bearing
        events that cannot be GDPR-compliant erased without destroying trace integrity.
\end{enumerate}

The file \texttt{xes-cryptographic-tombstoning.md} provides the wasm4pm remediation
specification: \texttt{Event<Encrypted<PII>>} is replaced by
\texttt{Event<Tombstoned<BLAKE3\_Receipt>>} via a typestate injection that preserves
trace integrity while satisfying the Right to be Forgotten (RTBF).

\paragraph{Blue River Dam rejection path tests.}
The file \texttt{public\_standards\_to\_blue\_river\_dam.md} defines the rejection paths
as formal conditions:
\begin{itemize}
  \item Fitness $f < 0.95$: transition rejected.
  \item Model unsound (dead transition or non-proper completion): transition rejected.
  \item 1-boundedness violated: execution core freezes and aborts.
  \item Fitness $f < 0.85$: rejected even with board override.
\end{itemize}
These are not aspirational thresholds; they are the conditions under which the
conformance checker halts and emits a rejection receipt.

\paragraph{WF-net soundness verification tests.}
The WF-net verification specification v30.1.2 (\texttt{wf-net\_verification\_specification.md})
defines the formal verification algorithms: Karp-Miller Coverability Graph construction
for detecting unbounded markings, short-circuited Petri net analysis for liveness
verification, and a production-grade Rust engine blueprint. The decommissioning receipt
example in this file records a completed verification:
\texttt{historical\_replay\_fitness: 0.978}, \texttt{precision: 0.912},
\texttt{total\_recorded\_cases: 124500}.

\subsection{Receipts}
\label{sec:standards-evidence-receipts}

The standards project emits receipts at four levels:

\paragraph{Checkpoint ledger entry.}
The primary receipt is the ledger block in \texttt{checkpoint\_\_public\_standards\_crosswalk\_complete.md}:
\begin{verbatim}
{
  "checkpoint_id": "chk-public-standards-crosswalk-001",
  "timestamp": "2026-05-31T23:59:59Z",
  "status": "PASSED",
  "standards_count_verified": 16,
  "standards_directory_hash":
    "e1f2g3h4...g9h0",
  "witness_signature": "SIG_ED25519_..."
}
\end{verbatim}

\paragraph{OTel span receipts.}
The \texttt{otel\_trace\_integration\_schema.json} defines a \texttt{blake3\_receipt}
field required on every OTel span, and an \texttt{event\_chain\_root} field holding the
BLAKE3 hash of the complete trace. These make receipt chaining continuous from the first
ingested span to process closure.

\paragraph{Trans-standard conversion receipts.}
Every conversion between standards emits a signed \texttt{LossReport}. The XES-to-OCEL
example records \texttt{synthetic\_objects\_created: 150}; the OCEL-to-XES example records
\texttt{discarded\_o2o\_links\_count: 450}, \texttt{pruned\_e2o\_links\_count: 1200},
\texttt{pruned\_object\_attributes\_count: 300}, and \texttt{duplicate\_events\_created: 80}.
These are named losses, not silent truncations.

\paragraph{Slide-to-Receipt bridge.}
Every M\&A presentation slide containing an operational claim is bound by:
$\text{SlideBinding} = \operatorname{BLAKE3}(\text{SlideUUID} \parallel \text{ReceiptHash}
\parallel \text{ClaimValue})$. This receipt is registered on the ledger and independently
replicable by the buyer's advisors within a $10^{-6}$ tolerance.

\label{sec:standards-evidence-checkpoints}
